# 클라이언트 설계 (현재 server.py 기준)

E2EE 1:1 채팅의 브라우저 클라이언트 설계 문서다. 서버(`server.py`)는 고치지 않고 **현재 서버 프로토콜에 맞춘다.**
팀 설계 문서(PDF "요구사항 분석 및 설계")와 달라지는 부분은 3장에 이유와 함께 정리했다.

---

## 1. 한눈에 보기

| 항목 | 결정 |
|---|---|
| 형태 | 브라우저 단일 페이지 (`client/index.html`), 외부 라이브러리 없음 |
| 암호 API | Web Crypto API (`crypto.subtle`) |
| 키 쌍 | ECDH P-256, **접속할 때마다 새로 생성**, 개인키는 내보내기 불가(`extractable: false`) |
| 키 파생 | ECDH 공유 비밀 → HKDF-SHA256 → **방향별** AES-256-GCM 키 2개 |
| 메시지 | AES-256-GCM, 메시지마다 96비트 랜덤 IV, 128비트 인증 태그 |
| AAD | 프로토콜 버전, 보낸 사람, 받는 사람, seq |
| 재전송 방지 | seq가 이전보다 커야 받아들임 |
| 중간자 대응 | 안전 번호(공개키 지문)를 양쪽 화면에 표시해 사람이 직접 비교 |
| 서버가 보는 것 | 닉네임, 공개키, 누가 누구에게 언제 보냈는지, `{ciphertext, iv, seq}` |
| 클라이언트만 아는 것 | 개인키, ECDH 공유 비밀, 세션 키, 평문 |

---

## 2. 실행 방법

```bash
pip install -r requirements.txt
python server.py                 # 0.0.0.0:8000 에서 대기
```

1. `client/index.html` 파일을 브라우저로 연다 (더블클릭). 창을 두 개 열어 서로 다른 닉네임으로 접속한다.
2. 서버 주소는 기본값 `ws://localhost:8000/ws` 그대로 둔다.
3. 한 창에서 왼쪽 목록의 상대를 눌러 대화를 시작한다.

**다른 PC에서 접속할 때:** 그 PC에서도 `client` 폴더를 복사해 `index.html`을 **파일로** 열고, 서버 주소에 `ws://<서버 PC IP>:8000/ws`를 넣는다. 서버 PC의 방화벽에서 8000 포트를 열어야 한다.

> **왜 파일로 여는가:** `crypto.subtle`은 보안 컨텍스트(HTTPS, `localhost`, `file://`)에서만 동작한다.
> 페이지를 `http://192.168.x.x:8000` 같은 주소로 열면 암호화 기능 자체가 없어서 접속 버튼이 비활성화된다.
> 파일로 열면 보안 컨텍스트이면서 서버에는 WebSocket으로만 붙는다.
> 덤으로 **서버가 클라이언트 코드를 내려주지 않으므로, 서버가 악성 JS를 심는 공격(PDF 10장)도 막힌다.**

## 3. 설계 문서(PDF)와 달라지는 점

현재 서버는 PDF 8장의 `hello` / `key_offer` / `key_accept` / `chat` 대신 `register` / `relay`를 쓰고,
relay payload에 `ciphertext`, `iv`, `seq` 외의 필드가 있으면 거부한다. 그래서 다음과 같이 맞췄다.

| 항목 | PDF | 이 클라이언트 | 이유 |
|---|---|---|---|
| 사용자 식별 | 서버가 발급한 임시 ID + 닉네임 | 닉네임이 곧 ID | 서버가 닉네임을 ID로 쓴다 |
| 키 쌍 수명 | 대화(세션)마다 | 접속마다 | 서버가 접속할 때 공개키 1개만 받는다 |
| 공개키 교환 | `key_offer` / `key_accept` | `register`로 등록, 서버가 `registered` / `peer_online`으로 배포 | 서버 구조 |
| HKDF salt | 세션별 랜덤, 상대에게 전달 | 두 공개키의 SHA-256 | 랜덤 salt를 보낼 통로가 없다 (5.3 참고) |
| HKDF info | conversation_id, 정렬한 ID, 공개키 해시, 방향 | 정렬한 ID, 방향 (공개키는 salt에 들어감) | conversation_id가 없다 |
| 봉투 | nonce, ciphertext, tag 분리 + conversation_id, message_id | `{ciphertext(태그 포함), iv, seq}` | 서버가 그 외 필드를 거부 |
| AAD | conversation_id, message_id, sender_id, recipient_id, 버전 | 버전, 보낸 ID, 받는 ID, seq | 받는 쪽이 알 수 있는 값만 쓸 수 있다 |
| 중복/재전송 감지 | message_id 중복 검사 | seq 증가 검사 | message_id를 보낼 수 없다 |
| 오류 형식 | `error {code, message}` | `error {reason}`, 등록 실패는 close 코드 4000~4003 | 서버 구조 |
| 상대 승인 | 미정 | 승인 절차 없음, 접속자 누구에게나 보낼 수 있음 | 서버에 승인 메시지가 없다 |
| 공개키 인증 | 미구현(후속 과제) | **안전 번호 표시 추가** | 서버를 안 바꾸고 할 수 있는 MITM 대응 |

| ID | 내용 | 상태 | 비고 |
|---|---|---|---|

| NFR-01~04 | 기밀성, 무결성, 키 보호, nonce 안전성 | 충족 | 11장 테스트로 확인 |

| NFR-07 | 모듈 분리 | 충족 | 4장 |
| NFR-08 | 외부 배포 시 WSS | 클라이언트는 `wss://` 주소 지원 | 서버 TLS 설정은 서버 담당 |

## 4. 모듈 구조

```
client/
├── index.html   화면 뼈대 (접속 화면, 채팅 화면)
├── style.css    스타일 (라이트/다크)
├── crypto.js    암호 모듈 E2EECrypto      ─┐ 서로 모름
├── relay.js     WebSocket 모듈 RelayClient ─┘
└── app.js       상태 관리와 화면 그리기 (위 두 모듈을 사용)
```

| 모듈 | 책임 | 하지 않는 것 |
|---|---|---|
| `crypto.js` | 키 쌍 생성, 공개키 내보내기/가져오기, ECDH, HKDF, 암호화/복호화, AAD, 안전 번호 | DOM, 네트워크. 그래서 Node에서도 그대로 테스트된다 |
| `relay.js` | 서버 연결, `register`, `relay`, 응답 짝짓기, 알림 이벤트 전달, 프레임 형식 검사 | 암호화. payload를 열어보지 않는다 |
| `app.js` | 접속자/대화 상태, 송신·수신 순서, seq 관리, 재전송 검사, 화면 표시, 검증 도구 | 직접적인 암호 연산 |

### crypto.js 공개 함수

| 함수 | 설명 |
|---|---|
| `generateKeyPair()` | ECDH P-256 키 쌍. 개인키 `extractable: false` |
| `exportPublicKey(pub)` | raw 65바이트(`0x04‖X‖Y`) |
| `importPublicKey(raw)` | 길이·접두 바이트 확인 후 가져오기. 곡선 위의 점이 아니면 `BAD_KEY` |
| `deriveSession({myId, myPrivateKey, myPublicRaw, peerId, peerPublicRaw})` | `{myId, peerId, sendKey, recvKey, safetyNumber}` |
| `encryptMessage(session, seq, text, sentAt)` | `{ciphertext, iv, seq}` (서버 relay payload 그대로) |
| `decryptMessage(session, payload)` | 인증 성공 시 `{text, sent_at}`, 실패 시 `CryptoError` |

`CryptoError.code`: `UNAVAILABLE`, `BAD_KEY`, `BAD_PAYLOAD`, `AUTH_FAILED`, `BAD_PLAINTEXT`

## 5. 암호 설계

이 장의 정의는 `tests/test_client_crosscheck.py`에서 Python `cryptography`로 따로 구현해 JS 결과와 일치하는지 확인한다.

### 5.1 키 쌍

- `crypto.subtle.generateKey({name: 'ECDH', namedCurve: 'P-256'}, false, ['deriveBits'])`
- 두 번째 인자 `false` 때문에 개인키는 `exportKey`가 거부된다. 개인키는 브라우저 탭 메모리 밖으로 나갈 방법이 없다.
- 공개키는 raw 65바이트를 표준 base64(88자)로 바꿔 `register`의 `pubkey`에 넣는다.
- 접속할 때마다 새로 만들고, 연결이 끊기면 참조를 버린다.

### 5.2 공유 비밀

- `deriveBits({name: 'ECDH', public: 상대공개키}, 내개인키, 256)` → 32바이트
- 이 값을 AES 키로 직접 쓰지 않고 HKDF 입력으로만 쓴다 (FR-06). 쓴 뒤에는 0으로 덮어쓴다.

### 5.3 HKDF-SHA256

두 사용자 ID를 문자열 순서로 정렬해 앞쪽을 `lo`, 뒤쪽을 `hi`라고 한다.
(서버가 ID를 ASCII와 한글 음절로 제한하므로 JS 문자열 비교와 유니코드 코드포인트 순서가 같다.)

```
IKM   = ECDH 공유 비밀 (32바이트)
salt  = SHA-256( pub_lo ‖ pub_hi )                         pub_* 은 raw 65바이트
info  = UTF-8( "e2ee-chat/v1|key|" + lo_id + "|" + hi_id + "|" + label )
label = "lo->hi"  (lo가 보내는 방향)   또는   "hi->lo"  (hi가 보내는 방향)
출력  = AES-256-GCM 키 (label별로 1개씩, 총 2개)
```

- 내가 `lo`면 송신키는 `lo->hi`, 수신키는 `hi->lo`. 반대도 같은 규칙.
- 송신키는 `['encrypt']`, 수신키는 `['decrypt']` 용도로만 만든다. 방향이 섞이면 API 단계에서 거부된다.
- 두 키 모두 `extractable: false`.
- ID에는 `|`가 들어갈 수 없으므로 (서버 규칙, 클라이언트도 다시 확인) info와 AAD의 구분이 모호해지지 않는다.

**salt를 공개키 해시로 정한 이유:** RFC 5869에서 salt는 비밀일 필요가 없고, 랜덤이 이상적이지만 없으면 고정값도 허용된다.
현재 서버에는 랜덤 salt를 상대에게 보낼 필드가 없다. 대신 키 쌍 자체가 접속마다 새로 만들어지므로 공유 비밀이 접속마다 달라지고,
salt에 두 공개키를 넣어 파생된 키를 "이 두 공개키로 만든 세션"에 묶는다.

### 5.4 메시지 암호화

```
평문  = UTF-8( JSON {"text": 메시지, "sent_at": 보낸 시각(ms)} )
IV    = crypto.getRandomValues(12바이트)      메시지마다 새로
AAD   = UTF-8( "e2ee-chat/v1|msg|" + 보낸 ID + "|" + 받는 ID + "|" + seq )
출력  = AES-256-GCM(송신키, IV, 평문, AAD) = 암호문 ‖ 태그(16바이트)
payload = { "ciphertext": base64(암호문‖태그), "iv": base64(IV), "seq": seq }
```

- Web Crypto는 태그를 암호문 뒤에 붙여 내놓는다. 서버가 별도 `tag` 필드를 받지 않으므로 붙은 채로 보낸다.
- `sent_at`은 평문 안에 있으므로 인증된다. 서버가 붙이는 `ts`는 인증되지 않으므로 화면에 쓰지 않는다.
- 메시지 길이는 2000자로 제한한다 (서버 암호문 상한 64KB보다 충분히 작게).

### 5.5 AAD에 넣는 값

받는 쪽이 독립적으로 알 수 있는 값만 넣을 수 있다.

| 값 | 받는 쪽이 아는 방법 | 막는 공격 |
|---|---|---|
| `e2ee-chat/v1` | 고정 | 다른 버전/용도의 암호문 재사용 |
| 보낸 ID | 서버가 붙인 `from` | 서버가 발신자를 바꿔치기 |
| 받는 ID | 자기 자신 | 다른 사람에게 보낸 메시지를 나에게 전달 |
| seq | payload의 `seq` | seq만 바꿔 재전송 검사를 우회 |

### 5.6 받은 메시지 처리 순서

1. 형식 검사: `seq`는 0 이상 정수, IV는 12바이트, 암호문은 16바이트 초과
2. AES-GCM 복호화 (태그 검증 포함). 실패하면 **아무 내용도 표시하지 않고** 폐기 표시
3. 평문이 `{text, sent_at}` 형식인지 확인
4. `seq > 마지막으로 받은 seq`인지 확인. 아니면 재전송으로 보고 폐기
5. 화면에 표시하고 `마지막으로 받은 seq` 갱신

`마지막으로 받은 seq`는 **인증에 성공한 경우에만** 올린다. 그래서 공격자가 seq를 크게 위조해 이후 정상 메시지를 막을 수 없다.

### 5.7 seq

- 상대별로 0부터 시작해 보낼 때마다 1씩 늘린다.
- 상대가 나가거나 새 키로 다시 들어오면 0으로 되돌린다 (새 세션이므로 새 키로 다시 시작).
- 서버는 한 연결의 프레임을 순서대로 처리하므로 정상 메시지는 seq 순서대로 도착한다.
- 클라이언트도 상대별로 보내기/받기 작업을 각각 한 줄로 세워(Promise 체인) 비동기 암호 연산 때문에 순서가 바뀌지 않게 한다.

### 5.8 안전 번호

```
digest = SHA-256( UTF-8("e2ee-chat/v1|fp|" + lo_id + "|" + hi_id + "|") ‖ pub_lo ‖ pub_hi )
digest 앞 30바이트를 5바이트씩 6묶음 → 각 묶음을 정수로 읽어 mod 100000 → 5자리 숫자
예) 94365 48170 35087 16389 53760 83415
```

양쪽 화면의 번호가 같으면 서버가 중간에서 공개키를 바꿔치기하지 않은 것이다. 직접 만나거나 전화로 비교한다.
상대가 재접속하면 키가 바뀌므로 번호도 바뀌고, 화면에 다시 확인하라는 경고가 뜬다.

### 5.9 IV 안전성 (NFR-04)

같은 키로 랜덤 96비트 IV를 쓰면 메시지 2³²개까지가 NIST SP 800-38D 권고 범위다.
키가 접속 단위로 바뀌므로 수업 시연에서 이 한도에 닿을 수 없다.

### 서버 → 클라이언트

| type | 필드 | 처리 |
|---|---|---|
| `registered` | `id`, `users: [{id, pubkey}]` | 접속 성공, 기존 접속자 목록 |
| `peer_online` | `id`, `pubkey` | 새 접속자. 이미 있던 ID면 재접속으로 보고 세션 초기화 |
| `peer_offline` | `id` | 그 상대와의 세션 키 폐기 |
| `message` | `from`, `payload`, `ts` | 복호화 시도 (5.6) |
| `ack` | `to`, `seq`, `delivered` | 내 relay에 대한 응답 |
| `error` | `reason` | 내 요청에 대한 오류 응답 |

등록 실패 시 서버는 오류 프레임 대신 close 코드로 연결을 끊는다:
`4000` 첫 메시지 형식 오류, `4001` 닉네임 형식, `4002` 닉네임 중복, `4003` 공개키 형식.

### 응답 짝짓기

`error` 프레임에는 어느 요청에 대한 응답인지 표시가 없다. 서버는 한 연결의 프레임을 순서대로 처리하고
요청 하나마다 응답(`ack`/`users`/`pubkey`/`pong`/`error`)을 정확히 하나 보내므로,
`relay.js`는 보낸 요청을 대기열에 넣고 응답을 도착 순서대로 짝짓는다.
기대한 종류가 아닌 응답이 오면 이후 응답을 믿을 수 없으므로 연결을 끊는다. 10초 동안 응답이 없어도 끊는다.

## 7. 상태 흐름

```
[접속 화면]
  닉네임 형식 확인 → 키 쌍 생성 → WebSocket 연결 → register
  └ registered 수신 → [채팅 화면], 기존 접속자 목록 표시
     └ close 4001~4003 → 접속 화면에 사유 표시

[채팅 화면]
  상대 선택 → 세션 키 파생(상대별 1번, 결과 보관) → 안전 번호 표시, "종단간 암호화" 배지
  메시지 보내기 → seq 할당 → 암호화 → relay → ack(전달됨 / 전달 안 됨) 또는 error(전송 실패)
  message 수신 → 5.6 순서로 처리 → 표시 또는 폐기 안내
                (대화를 열지 않은 상대면 안 읽음 숫자 증가, 처음 받을 때 세션 키 파생)

  peer_offline        → 세션 키·seq 폐기, "오프라인" 배지, 입력창 비활성
  peer_online(같은 ID) → 세션 초기화, "새 키로 대화하므로 안전 번호를 다시 확인하세요" 경고
  내 연결 끊김         → 모든 세션 키와 내 키 쌍 참조 폐기, "다시 접속" 버튼 (새 키 쌍으로 시작)
  나가기              → 연결 종료, 상태 전체 폐기, 접속 화면으로
```

## 8. 오류 처리

| 상황 | 화면 표시 |
|---|---|
| Web Crypto 사용 불가 (보안 컨텍스트 아님) | 접속 화면에 안내, 접속 버튼 비활성 |
| 닉네임 형식 오류 | 서버에 보내기 전에 거부 |
| 닉네임 중복 (close 4002) | "이미 사용 중인 ID" |
| 서버에 연결 불가 (close 1006) | "서버에 연결할 수 없거나 연결이 끊어졌습니다" |
| 상대 공개키가 잘못됨 | 대화 헤더에 "키 오류" 배지, 전송 불가 |
| 인증 실패 (변조, 키 불일치) | 빨간 안내 "메시지 1건을 폐기했습니다", 내용은 표시하지 않음 |
| 재전송 감지 | 노란 안내 "재전송된 메시지를 감지해 폐기했습니다" |
| 보내는 중 상대가 나감 | 해당 메시지에 "전송 실패" + 서버 사유 |
| 서버가 상대에게 전달 못 함 (`delivered: false`) | "상대에게 전달되지 않음" |
| 서버 연결 끊김 | 상단 빨간 배너 + "다시 접속" 버튼 |

모든 문자열은 `textContent`로 넣으므로 상대가 HTML이나 스크립트를 보내도 글자 그대로 보인다.
`index.html`에는 외부 스크립트·인라인 스크립트를 막는 CSP도 걸려 있다.

## 9. 보안 검증 기능과 시연 절차

### 화면에 있는 검증 기능

- **서버로 보낸 데이터 / 서버에서 받은 데이터:** 메시지마다 펼치면 실제로 오간 JSON이 보인다. 서버가 보는 것이 이것뿐이라는 설명에 쓴다.
- **보안 검증 도구 → 다음 메시지 1건 변조:** 암호화가 끝난 뒤 보내기 직전에 한 곳을 바꾼다. 전송 구간에서 누군가 값을 바꾼 상황을 흉내 낸다.
  - 암호문 1비트 / 인증 태그 1비트 / IV 1비트 / seq 값(AAD)
  - 받는 쪽에 "인증 태그 검증 실패"로 폐기 안내가 뜨고 내용은 보이지 않는다. 다음 정상 메시지는 그대로 도착한다.
- **마지막 메시지 그대로 재전송:** 이미 받은 정상 암호문을 한 번 더 보낸다. 받는 쪽은 인증은 통과하지만 seq로 걸러낸다.
- **안전 번호:** 두 창의 번호가 같은지 보여 주고, 재접속하면 바뀌는 것을 보여 준다.
- **내 공개키:** 서버가 아는 값은 공개키뿐이라는 것을 보여 준다.

### 서버 로그 확인

서버 콘솔에는 다음만 찍힌다. 평문을 보낸 문자열로 검색해도 나오지 않는다.

```
JOIN   id=김정현  pubkey=BHMrc6BwApw7Bqsh8GBy5LQ7…  (online=1)
RELAY  김정현 -> 윤내영  bytes=156  iv=luS7N2KmGaU9yGrK  ct=lgdc0s0ir9SVwtKlHRBAdSK4kko4/xjL…
RELAY  김정현 -> 윤내영  bytes=156  iv=luS7N2KmGaU9yGrK  ct=lgdc0s0ir9SVwtKlHRBAdSK4kko4/xjL…   ← 재전송 시연
LEAVE  id=김정현  (online=1)
```

### Wireshark 확인

1. 캡처 인터페이스를 루프백으로 고른다. Windows는 Npcap 설치 때 "loopback traffic capture" 옵션을 켜야 `Adapter for loopback traffic capture`가 보인다. macOS는 `lo0`.
2. 표시 필터: `websocket`
3. 검색할 메시지는 **영문·숫자 표시**를 넣어 보낸다 (예: `PLAINTEXT-TEST-1234`). 한글은 인코딩 옵션 때문에 검색이 헷갈린다.
4. Edit → Find Packet에서 **검색 위치를 "Packet details", 종류를 "String"**으로 두고 검색한다.

> **주의: 클라이언트 → 서버 WebSocket 프레임은 RFC 6455에 따라 마스킹된다.**
> 원시 바이트("Packet bytes")에서 검색하면 평문이었더라도 검색되지 않으므로 증거가 되지 않는다.
> 반드시 Wireshark가 마스킹을 푼 내용(Packet details, 또는 바이트 창의 "Unmasked data" 탭)에서 찾는다.
> **양성 대조:** 같은 방법으로 닉네임(영문으로 접속)을 검색하면 `register` 프레임에서 **찾아진다.**
> "닉네임은 찾아지는데 메시지는 안 찾아진다"를 함께 보여 줘야 검색 방법이 맞다는 것까지 증명된다.

시연은 `ws://`(TLS 없음)로 하는 것이 맞다. `wss://`로 하면 Wireshark에는 TLS 암호문만 보여 "서버도 내용을 볼 수 없다"를 보여 줄 수 없다.
실제 배포에서는 `wss://`를 써야 한다는 점은 발표에서 언급한다.

## 12. 서버 담당에게 전달할 사항

서버는 고치지 않았다. 클라이언트가 의존하는 동작과, 참고할 점만 적는다.

- **응답 순서:** 클라이언트는 "요청 하나에 응답 하나, 보낸 순서대로"에 의존한다 (6장). `relay` 실패 시 `error`에 `seq`를 같이 넣어 주면 더 견고해진다.
- **`/` 경로:** `test_client.html`을 찾지만 이 클라이언트는 파일로 열어 쓰므로 필요 없다.
- **프레임 크기:** `len(raw) > MAX_FRAME_BYTES`는 바이트가 아니라 글자 수를 센다. 한글이 많으면 실제 바이트가 최대 3배까지 커진다.
- **로그:** IV 전체와 암호문 앞 32자를 남긴다. FR-11(전체 암호문을 남기지 않음)은 충족하며, 시연용으로 "로그에는 암호문만 있다"를 보여 주기 좋다.
